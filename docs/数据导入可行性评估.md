# 数据导入可行性评估（第 251 轮巡检，数据自主权域 / 评估视角）

> 评估范围：第 250 轮 `data.exportAll` 产物（`hduonline-data-export` JSON 快照）能否/应否走「导入」回写，以及既有 dashboard 备份导入通道（`BACKUP_APP_ID`）的防呆现状。**只评估不落地导入功能**——结论与裁决建议供用户决策。

## 0. 结论（先行）

**无需新导入功能。** 既有 dashboard 备份导入通道已覆盖「恢复」场景（全量备份 ZIP / JSON，`import.run` 事务回滚 + 写库前校验）；`data.exportAll` 轻量快照按第 250 轮裁决定位为「查阅留档」，不用于导入（app 标识刻意不同，导入通道按 `app !== BACKUP_APP_ID` 直接拒绝，单测锁定）。本轮仅落地一处最小防呆：dashboard 导入入口的**文件体积前置校验**（512MB，读内存前拒绝），评估其余风险点均已有闭环（见下文逐项）。

## 1. 现状盘点（探查基线）

| 通道 | 实现 | app 标识 | 用途 |
|---|---|---|---|
| 全量备份 ZIP / JSON | `exporters.exportBackup`（dashboard 数据管理页导出）+ `import.run`（导入） | `BACKUP_APP_ID` | 换机 / 重装恢复：IndexedDB 全 store 逐段（含转写 / 流水明细）+ 截图二进制 |
| 全量数据导出 JSON | `data.exportAll` → `assembleExportPayload`（core/export/dataExport.ts，第 250 轮） | `hduonline-data-export` | 查阅 / 留档 / 自主持有：17 键白名单偏好 + 10 段轻量资产，**不含**转写 / 流水 / 截图 |
| 其他导出 | 复习卡片 md、收藏 CSV、大纲 md、周报月报 md 等 | 无结构化回读 | 单向输出，无导入语义 |

导入实现要点（core/export/importer.ts）：
- `parseBackupPayload`：JSON 合法性 → `app` 匹配 → `version` 整数且 ≤ `BACKUP_FORMAT_VERSION` → `dbVersion` ≤ `DB_VERSION` → `normalizeTables` 结构预校验（**全部在写库之前**完成，任何失败抛 `AppError` 且现有数据不受影响）。
- `runImport`：merge（按主键 `put` 覆盖）/ replace（先清 16 个 store 再写）两种模式，全部写入在**同一 IndexedDB 事务**内（`db.transaction([...IMPORT_STORES], 'readwrite')`，`tx.done` 提交、异常 `tx.abort()`）——任一写入失败整体回滚，含 replace 的清空操作。
- 兼容约定：旧备份缺新 store 段视为空段；新备份带未知段忽略（只读已知字段）；后补 store 防御式逐行校验（坏条目跳过并计数，不整体拒绝）。

## 2. 字段级冲突策略（同 id 存在 → 跳过 / 覆盖 / 合并）

| 策略 | 行为 | 优点 | 缺点 | 现状 |
|---|---|---|---|---|
| 跳过（skip） | 同 id 已存在则保留现有行 | 零覆盖风险 | 「恢复」语义下不完整；同 id 内容分叉时用户无从选择 | 未实现 |
| 覆盖（overwrite） | 同 id 以导入行替换（`put` 主键语义） | 恢复语义完整、实现最简 | 本机较新的修改被旧备份静默回退 | **merge 模式现状**（`put` 天然覆盖） |
| 合并（merge-fields） | 同 id 逐字段深合并（如收藏只补 tags、笔记只补 text） | 粒度最细 | 字段级冲突无解（双方同字段都改过时仍需二选一）；对 16 个 store 逐一定义合并规则复杂度高、可测性差 | 未实现 |

**建议**：维持现状（覆盖 = `put`）。理由：①导入场景主体是「换机恢复」（本机无数据）与「回滚到备份」（用户主动选择旧状态），覆盖语义都与场景吻合；②merge-fields 的字段级冲突本质仍需用户裁决，交互复杂度与收益不成比例；③replace 模式已提供「整库对齐备份」的强语义，与 merge 覆盖构成足够的选择空间。若未来要加「跳过」模式，实现成本低（写前 `get` 判存在），可作为独立立项。

## 3. 外键完整性（孤儿策略）

- `notes.favoriteId` / `reviewJobs.favoriteId` 引用收藏：既有约定「复习作业在收藏软删时一并删除」（period.ts 注释），store 内自洽。
- 导入场景孤儿来源：**只有 replace 模式全量写入时不存在孤儿**（所有段一起换）；merge 模式下若备份与本机的收藏 id 空间分叉（理论上可能：不同机器各自删除/重建收藏），导入的 reviewJobs 可能引用本机已不存在的 favoriteId。
- 孤儿后果盘点（消费方兜底现状）：复习视图对 favorite 缺失的作业有「收藏已被删除」防御路径；笔记列表按 favorite 存在性过滤。孤儿不崩溃、不渲染脏行——**当前影响可控**。
- `data.exportAll` 若做导入（本轮裁决不做）：其段集与备份不同（无 transcripts/chats 等），但 favorites/notes/reviewJobs 全量随行，孤儿风险与备份 merge 相同。

**建议**：维持现状（消费方已兜底，孤儿不致错）。若未来做导入增强，可加一步「导入后孤儿清扫」：merge 完成后对 reviewJobs/notes 做一次引用存在性过滤（在导入事务内执行，保持原子性）。

## 4. 部分失败回滚（Dexie / IndexedDB 事务能力探查）

- db 封装（core/db/index.ts）为 Dexie 风格的 IndexedDB 原生事务包装：`db.transaction([...stores], 'readwrite')` 返回事务对象，`tx.done` Promise 化提交；`runImport` 在 catch 中 `tx.abort()`。
- **IndexedDB 原生事务本身跨 store 原子**（同源同版本下 16 个 store 一个事务），不依赖 Dexie 的 tx 声明式回滚——部分失败（如中途 quota 超限 `QuotaExceededError`）会整体中止，清空操作一并回滚。importer 对 quota 错误有专门转译（`STORAGE_QUOTA`「本机存储空间不足，导入已回滚」）。
- 唯一的事务外环节：`stageImportJob`（页面把文件写进 `exportJobs` 表）发生在事务前——失败只留下一条过期作废的 job 记录（30 分钟 TTL 清扫），不影响数据。

**结论**：回滚能力完备，无缺口。

## 5. 体积上限（IndexedDB 容量 / 大 JSON 解析）

- IndexedDB 容量走浏览器配额（`storage.usage` op 已如实上报 `quotaBytes`），Chrome 对 extension origin 通常给磁盘可用空间的可观份额，全量备份（含截图二进制）现实中在百 MB 级。
- 大 JSON 解析的真实风险在**内存与主线程**：`JSON.parse` 是同步操作，超大文本会卡死调用线程。当前链路：UI `file.text()` 读入字符串 → 写入 exportJobs → background `JSON.parse` —— 两处都是整文件内存驻留。
- **本轮落地**：UI 侧 `MAX_IMPORT_FILE_BYTES = 512MB` 前置校验（`file.size` 检查，读内存之前拒绝，toast 明确提示且不触碰数据）——只拦「误选文件」（如改名 .json 的视频），不拦合法备份（正常备份远小于此上限）。结构 / 版本类校验维持 background 侧（写库前）不变。

## 6. 安全（导入 JSON 的字段注入面）

- **主键 / 关键字段已校验**：`normalizeTables` 对主键、类型关键字段做写库前断言（缺主键的行整体拒绝）。
- **已知面：非关键字段原样写回**——校验只断言「消费方依赖的字段」，其余字段随行写入 IndexedDB。影响面评估：读取方全部按已知字段取值（无 `Object.assign` 进全局 / 无 eval / 无 innerHTML 直接注入路径），脏字段只是「被存储的死数据」，不构成执行面；原型污染向量需要「字段名 `__proto__` 被展开合并」的代码路径，导入链路是逐行 `put` 存储、非对象展开，不命中。
- **白名单校验的必要性评估**：对「存储后死数据」做字段白名单的边际收益低（不影响行为），但会显著提高维护成本（16 个 store × 每次字段演进同步白名单）。**建议维持「关键字段断言 + 消费方防御」现状**；若未来引入「导出文件渲染预览」之类把导入数据直接喂给富文本渲染的功能，届时再对涉事字段做白名单（按需收口）。

## 7. 逐项风险总表

| 风险点 | 现状 | 评估 | 本轮动作 |
|---|---|---|---|
| 字段冲突 | merge=覆盖 / replace=整库 | 语义吻合场景，维持 | 无（评估归档） |
| 孤儿引用 | 消费方已兜底 | 影响可控 | 无（评估归档） |
| 部分失败 | 单事务原子回滚 | 完备 | 无（评估归档） |
